# 読ませるページの書き方（調べたことと、このサイトの決まり）

このサイトの文章を書く・直す人のためのメモです。ウェブの読まれ方と、読みやすい文章について調べたことをまとめ、それをこのサイトでどう使っているかを書いています。

## 1. 調べてわかったこと

### 人はウェブのページを「読まずに拾い読みする」

- ユーザビリティの研究で知られるヤコブ・ニールセンの 1997 年の調査では、利用者の 79% が新しいページを拾い読み（スキャン）し、一語ずつ読んだのは 16% だけでした。勧められていたのは、強調したキーワード、意味のある小見出し、箇条書き、一段落に一つの考え、結論を先に書く「逆ピラミッド」、ふつうの半分以下の文字量です。（[How Users Read on the Web](https://www.nngroup.com/articles/how-users-read-on-the-web/)）2020年に、13年分の視線計測をもとに見直した記事でも、人が拾い読みすることは変わっていないと確かめられています。（[How People Read Online: New and Old Findings](https://www.nngroup.com/articles/how-people-read-online/)）
- 視線の研究では、見出しと小見出しを拾い、気になったところだけ本文を読む「レイヤーケーキ型」の読み方が知られています。見出しがはっきりしていて、中身を表しているときに起きる読み方です。（[Text Scanning Patterns](https://www.nngroup.com/articles/text-scanning-patterns-eyetracking/)）
- 2018 年の調査では、ページを見ている時間のおよそ 74% が、最初の2画面に集中していました。1920×1080 の画面での結果で、スマートフォンは調べていません。（[Scrolling and Attention](https://www.nngroup.com/articles/scrolling-and-attention/)）

→ **見出しだけ、要点だけを拾っても話がわかるようにする。いちばん大事なことはページの初めに置く。**

### 結論を先に、文は短く

- 木下是雄[『理科系の作文技術』（中公新書, 1981）](https://ndlsearch.ndl.go.jp/books/R100000002-I000001522014)は、大事なことを先に書く「重点先行主義」と、短い文で書くことを説いています。読む人が、続きを読むべきかをすぐ判断できるようにするためです。
- 日本語の読みやすさの研究では、文の長さと漢字の割合が大きく効くとされてきました。このサイトでは、漢字が5字以上続いたら切ることを目安にしています（出典のある基準ではなく、書く人の目安です）。

→ **章も段落も、結論から書く。一文に一つのことだけ。漢字が続いたら、ひらがなや言い換えで切る。**

### 問いかけと、身近な例

- 心理学者ローウェンスタインの「情報の空白」の考え方（[1994](https://doi.org/10.1037/0033-2909.116.1.75)）によると、好奇心は「知っていることと知りたいことの間のすき間」に気づいたときに生まれます。ただし、すき間が大きすぎても小さすぎても働かず、少しは知っていて、答えにたどり着けそうなときに強くなります。
- 抽象的な考えは、具体的な例と一緒に学ぶと理解しやすく、新しい場面にも当てはめやすくなることが、学習の研究で確かめられています（[Rawson ほか, 2015](https://doi.org/10.1007/s10648-014-9273-3)。2022年の追試でも、初めて見る例を見分ける力が上がりました（効果量 d=0.30、[Micallef & Newton](https://doi.org/10.1177/00986283211058069)））。ただし、例を抽象の前に置くべきか、例を何個にすべきかまでは示していません。

→ **問いかけは、読者が知っている身近なことについて聞き、すぐ後で答える。抽象的な話には、具体的な例を添える。**

### 文字の組み方

- アクセシビリティの国際基準 WCAG 2.2 の達成基準 1.4.8（AAA）は、一行の長さを 80 字以内（日本語などは 40 字以内）、行間を 1.5 倍以上、段落の間をそれ以上にすることを挙げています。両端そろえも避けるよう書かれています。（[Understanding SC 1.4.8](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation)）

→ **本文は一行 36 字前後、行間は 2 倍前後にしている（`src/styles/global.css` の `.longform`）。**

## 2. このサイトの決まり

### ページの組み立て

1. **最初に、まとめを置く。** トップページの「設計会の考え方」は、各章の見出しと要点から自動で作られます。
2. **文脈から並べる。** 読む人は、前の章を前提に次の章を読みます。章は、前の章が次の章の前提になる順に並べます。知らない言葉や考えを、説明する前に使わないようにします。
3. **トップページは、1ページで「わかる」から「興味がわく」までを担う。** 読者の大半はトップページしか見ません。だからトップページは長文にし、設計とは何か、なぜ今大事か、設計会で何ができるかまでを、章を重ねて伝えます。ヒーローの最初の一文は設計の価値から書き、AI は「つくる手間が下がった例の一つ」として扱います。
4. **トップ以外のページは、1ページ1テーマ。** ページの主張を一文で言え、それを lead か最初の要点に書きます。章は、その一文を支えるものだけにします。話題が2つ以上になったら、ページを分けます（設計の工程は、1工程1ページにしています）。分けたページどうしは、行き来しやすいようにつなぎます。
5. **章は「問い → 主張 → 要点 → 本文」の順。** 章の上の小さな文字（eyebrow）は読者が心の中で持っている問い、見出しはそれに答える主張、すぐ下に要点を置きます。
6. **見出しは主張の形で書く。** 「データ分析について」ではなく「数字は同じでも、形はまったく違う」。見出しを上から読むだけで、話がつながるようにします。
7. **大事さに合わせて見た目を変える。**

   | ブロック               | いつ使うか                                                               | 見た目                                         |
   | ---------------------- | ------------------------------------------------------------------------ | ---------------------------------------------- |
   | `point`（要点）        | その部分でいちばん言いたいこと。拾い読みする人はここだけ読む             | オレンジの線                                   |
   | `question`（問いかけ） | 身近なことを聞いて、続きを読みたくさせる。答えは `answer` に（隠さない） | 「？」の印と、すぐ下の答え                     |
   | `example`（例）        | `kind: real` は実際にあった例（出典必須）、`kind: scene` は説明の場面    | 灰色の箱（「実際にあった例」「たとえば」の札） |
   | `heading`（小見出し）  | 章の中で話が切り替わるところ                                             | 黒い四角                                       |
   | `aside`（補足）        | 本題ではないが分量の多い補足や、詳しい事例                               | 折りたたみ                                     |
   | `p`（段落）            | 本文。一段落に一つの考え。短い補足や出典は `note` に                     | `note` は本文の右                              |

8. **読み方を読者に説明しない。** 「3分で読める」「読み飛ばしてもよい」のような、読み方の指示は書きません。拾い読みしやすさは、見出し・要点・見た目で実現します。「架空の例です」のように、内容の性質を明かす文は読み方の指示ではないので書きます。
9. **折りたたみは読まれにくい。** 折りたたみ（`aside`）は開かれずに読み飛ばされることが多いので、読んでほしいもの（問いかけの答えなど）は入れません。本題でない長い補足や、詳しい事例だけを入れます。短い補足や出典は、段落の `note`（本文の右）に書きます。
10. **主張には、実際にあった例を添える。** 実際にあった例は `example` に `kind: real` と書き、`source` に出典のリンクを書きます。数字が資料によって違うときは、控えめな方を使います。説明のための場面（部室の予約や、設計の流れの例のページ）は `kind: scene`（省略してよい）にし、架空なら題か lead にそう書きます。
    **架空の例は、未来の計画として書きます。** 「もし設計会でイベントの企画を設計するなら、こう進めます」という形です。起きていない出来事を「アンケートを読むと〜という声が多かった」「試すと説明に5分かかった」のように過去の形で書くと、存在しない過去の話になり、読む価値がなくなります。調べた結果や試した結果は「たとえば〜という声が多ければ、問題は〜と書ける」「説明が2分に収まらなければ、カードにまとめ直す」のように仮定で書き、数字は計画のための仮の値だと明かします。観察の記録の書き方を見せるカードのように、見本として過去の形で書くものは、見本だと明かします（`npm run check:content` が、事例のページと場面の例の過去形を見つけます）。
11. **実例は、一つの主張に1件（多くて2件）。** 調べると例はいくらでも見つかりますが、並べすぎると主張が薄まります。出典を確かめた例のうち、いちばん強く、読者（岡山の大学生）に身近なものを選びます。同じ実例は1ページにだけ置き、ほかのページからはそのページへリンクします（`npm run check:content` が、同じ出典の実例が2ページにあると知らせます）。
12. **イメージしにくいところには図を置く。** 人物やキャラクターの挿絵（イラスト）は使いません。アイコンと説明の図は使ってよいです。図は `src/components/figures/` に、機能の図は `idef0` ブロックで描きます。外部の画像は必要最低限にし、ライセンスを確かめて `docs/image-credits.md` に書きます（載っていない画像があると `npm run check:content` が失敗します）。
13. **関連授業は補足として添える。** 学内の授業とのつながりは親近感につながります。ページごとに5件まで、いちばん関係の深いものを選びます。
14. **設計会の趣旨から外れる話は足さない。** 調べてわかった面白い話でも、設計会の活動（実装の手前までの設計）につながらないものは、ページを薄くするので入れません。

### 想定する読者

頭のいい大学生です。やさしく書くことと、中身を薄くすることは違います。正しい用語、実際の仕組み、数字、手法の名前とその理由は省かずに書き、初めて出てくる用語はその場で言い換えます。

### 出典

- 出典は、必ずリンクを付けて書きます。URL のない出典は使いません。見つからないときは、その出典に頼る主張ごと書きません。
- 段落の注（`note`）、例の出典（`source`）、図の出典では `[表示名](https://…)` と書きます。参考文献（`references`）には `url` を書きます。注と例の出典の文字数は、表示される文字だけを数えます（URL は数えません）。
- リンク先は、DOI、出版社・規格団体・官公庁・博物館などの公式のページを優先します。本は、国立国会図書館サーチか CiNii の書誌ページにリンクします。
- トップページでは図の番号・題・説明を省きますが、出典は図の下に小さく出します。
- 図の出典にリンクがあるかは `npm run check:sources` で、文章の注や参考文献は `npm run build` で確かめられます。リンク先が開けるかは、年度の初めに `npm run check:links` で確かめます（シラバスのリンクも含みます）。

### 文の書き方

- 二重否定や遠回しな否定は使わない。A と言いたいのに「A でないことはない」「￢A ではない」と書くと、読む負担が増える（例：「無駄にならない」→「役に立つ」）。ただし、誤解を正す否定（「相関は因果を意味しない」）や、肯定に言い換えると意味が変わる否定（「難しくない」と「やさしい」は違う）は、否定のままでよい。言い換えるときは、言い過ぎにならないかも確かめる。
- 単語は正しい意味で使う。専門用語は、分野の定義（規格・教科書）に合っているかを確かめてから使う。
- 文脈を先に置く。章や段落は「なぜその話をするのか（前の話とのつながり）」から始め、用語は使う前に説明する。
- 一文は短く。読点（、）で3つ以上つながったら、文を分ける。
- 専門用語は、初めて出てきたところで言い換える（例：「要件（設計が満たすべき条件）」）。
- 「〜と言われています」は、出どころがはっきりしない数字に使う。確かめた数字は言い切る。
- 強調（`**…**`）は一段落に1か所まで。多すぎると、どこも目立たなくなる。
- 身近な例は、読者（大学生）の生活から選ぶ。授業の課題、サークル、アルバイト、家の中のもの。業界の話は補足に回す。
- 用語は一つの言い方にそろえる（「要件」と書いたら、同じものを「条件」「要求」と言い換えない）。言い換えてよいのは、決め台詞や修飾の言葉（「価値」「考え抜く」など）だけ。決め台詞は、ここぞという1か所だけにする。
- 問いかけの答えは、すぐ後に書く（答えはいつも見えている）。
- 鉤括弧で引用するのは、原文で確かめた言葉だけにする。原文が確かめられないときは言い換え、「（要旨）」と添える。括弧の中の括弧は『』にする。
- 同じ言い回しを、すぐ近く（同じ画面や、要点と本文）で繰り返さない。要点で言い切ったことは、本文では理由や例で支える。
- 用語は、説明してから使う。例の中で先に使うなら、ふつうの言葉で書き、その後で用語を当てる（「見方」→「ここでは『視点』と呼びます」）。
- 読者を突き放す言い方をしない。たとえば「センスではなく論理」は、デザインを学ぶ人には「センスは要らない」と読める。「センスだけでなく」と書く。

### 「設計を知る」のページ

- 決まった章立てはありません。そのテーマが**いちばん伝わる順番**で書きます。多くのページは「身近な問い → 何なのか → なぜ大事か → どう使うか → いま → 設計会では → 寄り道（歴史）」の順ですが、合わなければ変えてかまいません。
- 新しいテーマは、`src/content/design/` に YAML を一つ足すだけで、一覧・地図・リンクに加わります。
  - 設計のプロセスの全体 … `layer: process`（「設計のプロセス」の一ページだけ）
  - 工程一つずつ … `layer: step`。`order` が工程の番号。ページの上に、ほかの工程へ移れる帯が出る
  - どの工程にも通じる視点 … `layer: lens`。`perStep` を書くと、地図の表に「工程ごとの使い方」が出る（書かなければ空欄）
  - 設計の流れの例 … `layer: case`。決まった型で書かず、5つの工程に合わせる必要もない。実際の設計では1つの工程に手順がいくつも入り、境界があいまいな手順もあるので、手順を順に並べ、設計として大事な手順は詳しく書く（文字数の制限はない）。手順を行った結果（選んだ案、決めた数値、問題の一文の中身、比べた点数など）は書かない。出てくる設計はグループや状況で違ってよく、押しつけるものではないからです。書くのは、何をするか、なぜ今するか、どうやるか、何に気をつけるか、どんな形のものができ、次の手順でどう使うかまで。冒頭では、目的・誰のため・計画の終わりにできるもの・届いたかの確かめ方を示す。章に `step: 番号` を書くのは、その手順が1つの工程にはっきり入るときだけ（工程のページへのリンクが付く）。これから取り組む計画として書く（「〜します」「〜なら」）
  - それ以外のテーマ … `layer: topic`

### 言葉と表記

言葉の使い方は、調べて確かめてから書きます。表記は、ふつうの文章と同じように漢字を基本にし、記号と数字は特別な理由がなければ半角にします（設計会の決定、2026年10月）。そのほかの点は文化審議会[「公用文作成の考え方」（2022年）](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf)と[JTF 日本語標準スタイルガイド](https://www.jtf.jp/tips/styleguide)を参考にしています。

| 項目             | 決まり                                                                                                                       | 例                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 漢字で書く語     | 意味を持つ語は漢字。分かる・良い・一番・全て・例えば・他・後・間・初めて・基に・気付く・身に付く・今・仕組み                 | 「わかる」→「分かる」、「よい」→「良い」                   |
| ひらがなのまま   | 「つくる」と「ものづくり」（設計会の言葉として決めたもの）                                                                   | 「作る」ではなく「つくる」（試作・製作のような熟語は漢字） |
| ひらがなのまま   | 文法の働きをする語：こと・もの・とき・ところ・ため・など・できる・ない、「〜ていく」「〜てみる」、副詞の「よく」（しばしば） | 「使うこと」「よく使われる」                               |

| よく揺れる語     | ウェブ（Web ではなく）、スマートフォン（スマホではなく）、使う人・利用者（使い手ではなく）                                   |                                                            |

数の書き方について：「公用文作成の考え方」は「一つ」「二人」のように訓で数える語を漢数字で書くのを原則としながら、広報などで明確に数を数えている場合は算用数字で書くこともあるとしています（解説 I-4）。拾い読みでは算用数字のほうが目に留まる（[Nielsen, 2007](https://www.nngroup.com/articles/web-writing-show-numbers-as-numerals/)）ので、このサイトは広報として算用数字を使います。「一つの主張」「ある一つの」のように「一つ」が「ある」の意味のときは、数を数えていないので漢数字のままにします。

表記の決まりのうち、機械で見つけられるもの（「Web」「スマホ」「使い手」「要求定義」、全角の記号、漢字で書く語のひらがな、数を数える漢数字、読み方の指示、二重否定の決まった形、一段落に2か所以上の強調）は、`npm run check:content` で確かめます（`npm run build` の前にも走ります）。

確かめた言葉の例：構想設計（概念設計）は「案を広げる」と「比べて選ぶ」を合わせた範囲を指すので、工程3は「発想」と呼んでいます。CAE は構造だけでなく流れや熱などの解析全般を指します。2024年に義務になったのは、求められたときの「合理的配慮」で、ウェブなどの「環境の整備」は努力義務です。
